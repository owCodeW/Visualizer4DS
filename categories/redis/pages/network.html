Redis 网络模型核心要点

⚡
单线程 Reactor
Redis 核心采用单线程事件循环模型 aeEventLoop， 通过 aeProcessEvents() 不断轮询就绪事件并分派回调。 单线程避免了锁竞争，保证命令顺序执行。
🔄
I/O 多路复用
使用 epoll(Linux) / kqueue(macOS) / select(fallback) 同时监听数千个连接的读写事件，一个线程即可高效处理海量并发。
🧵
I/O 线程 (6.0+)
Redis 6.0 引入 io-threads，将客户端读写分摊到多个 I/O 线程并行处理， 但命令执行仍在主线程，保证数据一致性。
📋
事件驱动
一切皆事件：客户端连接是文件事件，EXPIRE 是定时事件， BGREWRITEAOF 由子进程通知主线程。所有逻辑由回调驱动。
💾
持久化不阻塞
RDB 通过 fork() + COW 由子进程完成； AOF 由主线程写入缓冲区，fsync 由后台线程完成（everysec 模式）。
🚀
为什么快
纯内存操作 + 单线程无锁 + I/O 多路复用 + 高效数据结构 + 管道/批量操作，单机 QPS 可达 10 万+。

aeEventLoop 事件循环

aeEventLoop 是 Redis 自己实现的轻量级事件循环库，核心数据结构包含文件事件表、定时事件链表和就绪事件队列。

// ae.h - 事件循环核心结构 typedef struct aeEventLoop { int maxfd; // 当前注册的最大 fd int setsize; // fd 集合大小 (等于 maxclients + 128) long long timeEventNextId; // 下一个定时事件 ID time_t lastTime; // 上次检查定时事件的时间 aeFileEvent *events; // 注册的文件事件数组 [fd] → 事件 aeFiredEvent *fired; // 已触发事件数组 (epoll_wait 返回) aeTimeEvent *timeEventHead; // 定时事件链表头 int stop; // 停止标志 void *apidata; // 平台多路复用数据 (epoll_fd 等) aeBeforeSleepProc *beforesleep; // 每轮循环前回调 aeBeforeSleepProc *aftersleep; // 每轮循环后回调 } aeEventLoop; // 文件事件 typedef struct aeFileEvent { int mask; // AE_READABLE | AE_WRITABLE aeFileProc *rfileProc; // 读回调 aeFileProc *wfileProc; // 写回调 void *clientData; // 关联的 client 指针 } aeFileEvent; // 定时事件 typedef struct aeTimeEvent { long long id; // 唯一 ID long when_sec; // 触发时间 (秒) long when_ms; // 触发时间 (毫秒) aeTimeProc *timeProc; // 回调函数 aeEventFinalizerProc *finalizerProc; void *clientData; aeTimeEvent *prev; // 双向链表 aeTimeEvent *next; } aeTimeEvent;

主循环流程

1
beforesleep 回调
每轮循环开始前执行，处理 unblockClient、flushAppendOnlyFile、 handleClientsWithPendingWrites 等待写数据等。
2
计算最近定时事件时间
遍历定时事件链表，找到最近要触发的定时事件，计算 tvp（超时值）， 作为 epoll_wait 的最大等待时间，避免定时事件延迟。
3
epoll_wait 阻塞等待
调用 aeApiPoll() → 底层 epoll_wait()， 等待就绪的文件描述符，最多阻塞 tvp 时间。返回就绪 fd 数组 fired[]。
4
分派文件事件
遍历 fired[]，根据 mask 调用对应的 rfileProc（读回调） 或 wfileProc（写回调）。如 readQueryFromClient、sendReplyToClient。
5
处理定时事件
遍历定时事件链表，对已到期的定时事件调用 timeProc。 如 serverCron（100ms 周期）处理过期 key、rehash、统计等。
关键设计：文件事件优先级高于定时事件。先处理所有就绪的文件事件，再处理定时事件。 这保证了客户端请求的响应延迟最小化。

I/O 多路复用机制

Redis 通过抽象层 aeApi 封装不同平台的多路复用实现，编译时自动选择最优方案。

特性 epoll (Linux) kqueue (macOS) select (Fallback)
时间复杂度 O(1) O(1) O(n)
最大连接数 无上限 (受系统限制) 无上限 (受系统限制) FD_SETSIZE (通常 1024)
触发模式 LT (水平) + ET (边缘) ET (边缘触发) LT (水平触发)
Redis 默认 首选 macOS 首选 仅兜底
内核拷贝 仅就绪事件 (mmap) 仅就绪事件 全量 fd_set 拷贝
Redis 选择策略：编译时按 epoll → kqueue → select 优先级自动选择。 生产环境几乎都是 Linux + epoll。Redis 使用 LT（水平触发）模式，简化编程模型。

命令处理全链路

1
acceptTcpHandler — 新连接接入
监听 fd 可读 → accept() 创建客户端 fd → 创建 client 结构体 → 注册 AE_READABLE 事件，回调为 readQueryFromClient。
2
readQueryFromClient — 读取请求
从客户端 fd 读取数据到 client.querybuf（SDS 动态缓冲区）。 Redis 7 支持 I/O 线程读取，此时由 IO 线程代读。
3
processInputBuffer — 协议解析
从 querybuf 中按 RESP 协议解析命令。 支持内联命令和 RESP 数组两种格式，解析后填充 client.argv[] 和 client.argc。
4
processCommand — 命令执行
查找命令表 redisCommandTable → 检查参数数、权限、内存限制 → 调用 cmd->proc() 执行具体逻辑 → 结果写入 client.buf 或 client.reply 链表。
5
addReply — 写入响应
响应数据先写入 client.buf（16KB 固定缓冲）或 client.reply 链表。 然后注册 AE_WRITABLE 事件，回调为 sendReplyToClient， 等待 fd 可写时异步发送。
6
sendReplyToClient — 发送响应
fd 可写 → write() 发送缓冲区数据 → 发送完毕后移除 AE_WRITABLE 事件。 如果发送不完整（EAGAIN），保留写事件等待下次可写。
// client 结构体中与网络相关的关键字段 typedef struct client { int fd; // 客户端 socket fd sds querybuf; // 查询缓冲区 (读入的原始数据) sds pending_querybuf; // I/O 线程读取后的待处理缓冲 int argc; // 命令参数个数 robj **argv; // 命令参数数组 struct redisCommand *cmd; // 解析后的命令对象 char buf[PROTO_REPLY_CHUNK_BYTES]; // 固定 16KB 响应缓冲 int bufpos; // buf 中已用字节数 list *reply; // 大响应用链表 (超过 buf 容量) unsigned long long reply_bytes; // 待发送总字节数 int flags; // CLIENT_* 标志位 } client;
RESP 协议：Redis 使用 RESP (REdis Serialization Protocol) 作为客户端-服务端通信协议。 简单字符串 +OK\r\n、错误 -ERR\r\n、整数 :1\r\n、 批量字符串 $6\r\nhello\r\n、数组 *2\r\n...。

Redis 6.0+ I/O 线程

Redis 6.0 引入 I/O 线程，将网络读写分摊到多线程，但命令执行仍在主线程， 保证数据一致性和命令顺序性。

📥
读线程化
io-threads-do-reads yes 开启读线程化。 主线程将客户端 fd 分配给 IO 线程，线程并行调用 read() 读取数据到 pending_querybuf。
📤
写线程化
命令执行后，主线程将待写客户端分配给 IO 线程， 线程并行调用 write() 发送响应。主线程等待所有 IO 线程完成。
🔒
无锁设计
每个客户端同一时刻只被一个线程处理（主线程或某个 IO 线程）， 通过 CLIENT_PENDING_READ / CLIENT_PENDING_WRITE 标志避免竞争，无需加锁。
# redis.conf — I/O 线程配置 # IO 线程数 (含主线程, 建议不超过 CPU 核数) io-threads 4 # 是否开启读线程化 (默认只开写线程化) io-threads-do-reads yes
注意：I/O 线程仅处理网络读写，不执行命令。 命令执行（processCommand）始终在主线程串行执行，保证原子性和数据一致性。 I/O 线程数建议设为 CPU 核数 - 1，不超过 8。

定时事件 & serverCron

Redis 的定时事件通过 aeTimeEvent 链表管理，最重要的定时回调是 serverCron， 每 100ms 执行一次，负责大量后台维护任务。

⏰
过期 Key 清理
每次执行 serverCron 时，从过期字典中采样 ACTIVE_EXPIRE_CYCLE_LOOKUPS_PER_LOOP 个 key， 逐步删除已过期 key。采用惰性 + 定期双重策略。
🔄
Rehash 渐进式
HashTable rehash 不是一次完成，而是分摊到 serverCron 和每次 CRUD 操作中， 每次迁移 1 个 bucket，避免长时间阻塞。
📊
统计信息更新
更新 instantaneous_ops_per_sec、内存使用、连接数等统计指标， 供 INFO 命令返回。
💾
AOF 重写触发
检查 AOF 文件大小增长比例，超过阈值自动触发 BGREWRITEAOF。 同时检查 RDB 快照条件。
🔗
主从复制心跳
主节点每秒向从节点发送 PING，从节点每秒发送 REPLCONF ACK。 检测超时、处理断线重连、传播写缓冲。
📡
Sentinel / Cluster
Sentinel 模式下执行故障检测、主观/客观下线判断。 Cluster 模式下执行 Gossip 心跳、故障转移、slot 迁移。

serverCron 执行频率

// server.h — 默认 100ms 一次 #define DEFAULT_HZ 10 // 每秒 10 次 → 100ms 间隔 // 可通过配置调整 // hz 100 → 每 10ms 一次 (更精确的过期清理) // hz 1 → 每 1000ms 一次 (更低 CPU 开销) // serverCron 返回值决定下次执行时间 int serverCron(struct aeEventLoop *eventLoop, long long id, void *clientData) { // 1. 更新服务器统计 (uptime, ops/sec, memory) // 2. 清理过期 key (active expire cycle) // 3. 渐进式 rehash // 4. 触发 AOF 重写 / RDB 保存 // 5. 处理 SIGTERM 优雅关闭 // 6. 主从复制超时检测 // 7. Cluster/Sentinel 定时任务 return 1000/server.hz; // 返回下次执行间隔 (ms) }
定时事件 vs 文件事件：Redis 优先处理文件事件（客户端请求），再处理定时事件。 如果某轮循环中文件事件处理耗时过长，定时事件会延迟执行，但不会丢失。 serverCron 的实际执行间隔可能略大于 100ms。

I/O 模型演进：从 BIO 到 epoll

Linux 网络 I/O 模型经历了 BIO → select → poll → epoll 四代演进， 每一代都在解决前一代的核心瓶颈。Redis 选择 epoll 作为最终方案。

第一代：BIO — 同步阻塞 I/O

// BIO 模型: 每个连接占用一个线程 while (true) { int clientFd = accept(serverFd, ...); // 阻塞等待新连接 pthread_create(&tid, NULL, handle_client, clientFd); } void* handle_client(int fd) { while (true) { int n = read(fd, buf, sizeof(buf)); // 阻塞等待数据 if (n <= 0) break; process(buf, n); write(fd, response, ...); // 阻塞等待发送 } }
核心问题：每个连接需要一个线程，1 万个连接就需要 1 万个线程。 线程栈默认 8MB，10K 连接 = 80GB 内存。线程上下文切换开销巨大，完全不可行。

第二代：select — 首次多路复用

// select 模型: 单线程监听多个 fd fd_set readfds; while (true) { FD_ZERO(&readfds); for (int i = 0; i < maxfd; i++) FD_SET(i, &readfds); // 每次都要重新构建 fd_set select(maxfd + 1, &readfds, NULL, NULL, NULL); // 阻塞等待, 全量拷贝到内核 for (int i = 0; i < maxfd; i++) { // 线性扫描所有 fd if (FD_ISSET(i, &readfds)) handle(i); } }
✅
解决了什么
单线程即可监听多个连接，不再需要一连接一线程。 引入了 I/O 多路复用的概念。
❌
三大缺陷
1. FD_SETSIZE=1024 硬编码上限
2. 每次调用需全量拷贝 fd_set 到内核（用户态→内核态）
3. 返回后需线性扫描 O(n) 找就绪 fd

第三代：poll — 突破 fd 上限

// poll 模型: 用 pollfd 数组替代 fd_set struct pollfd fds[MAX_FDS]; // 动态数组, 无 1024 限制 nfds_t nfds = 0; while (true) { poll(fds, nfds, -1); // 仍然全量拷贝到内核 for (int i = 0; i < nfds; i++) { // 仍然线性扫描 if (fds[i].revents & POLLIN) handle(fds[i].fd); } }
改进与不足：poll 用 pollfd 结构体数组替代了位图 fd_set， 突破了 1024 上限。但仍然每次全量拷贝 + 线性扫描 O(n)， 万级连接时性能依然不理想。

第四代：epoll — 事件驱动 O(1)

epoll 是 Linux 2.6 引入的终极方案，通过红黑树 + 就绪链表 + mmap 共享内存 彻底解决了 select/poll 的所有问题。Redis 的 aeEventLoop 底层即使用 epoll。

epoll 三大 API

// 1. 创建 epoll 实例 int epfd = epoll_create(1024); // 内核创建: 红黑树 (存 fd) + 就绪链表 (存就绪事件) + mmap 共享区 // 返回 epoll 文件描述符 epfd // 2. 注册/修改/删除 fd struct epoll_event ev; ev.events = EPOLLIN | EPOLLET; // 监听读事件 + 边缘触发 ev.data.fd = clientFd; epoll_ctl(epfd, EPOLL_CTL_ADD, clientFd, &ev); // O(log n) 红黑树插入, 只注册一次, 不用每次重新传 // 3. 等待就绪事件 struct epoll_event events[MAX_EVENTS]; int n = epoll_wait(epfd, events, MAX_EVENTS, timeout); // 只返回就绪的 fd, 不需要遍历所有 fd // O(1) — 就绪多少返回多少, 与总 fd 数无关 for (int i = 0; i < n; i++) { handle(events[i].data.fd); // 只处理就绪的 }

LT (水平触发) vs ET (边缘触发)

对比项 LT (水平触发) ET (边缘触发)
通知时机 缓冲区有数据就持续通知 仅新数据到达时通知一次
读方式 可部分读，下次继续通知 必须一次读完 (非阻塞循环读)
编程复杂度 简单 不怕漏读 复杂 漏读则等下次新数据
系统调用次数 较多 (每次通知都 epoll_wait) 较少 (一次通知处理完)
Redis 选择 LT 简化编程模型 —
Nginx 选择 — ET 追求极致性能

Redis 中 epoll 的使用方式

// ae_epoll.c — Redis 对 epoll 的封装 // 1. 创建 epoll 实例 static int aeApiCreate(aeEventLoop *eventLoop) { aeApiState *state = zmalloc(sizeof(aeApiState)); state->epfd = epoll_create(1024); // 创建 epoll 实例 state->events = zmalloc(sizeof(struct epoll_event) * eventLoop->setsize); eventLoop->apidata = state; return AE_OK; } // 2. 注册/修改 fd 事件 static int aeApiAddEvent(aeEventLoop *eventLoop, int fd, int mask) { struct epoll_event ee; int op = (prevmask == AE_NONE) ? EPOLL_CTL_ADD : EPOLL_CTL_MOD; ee.events = 0; if (mask & AE_READABLE) ee.events |= EPOLLIN; // 读事件 if (mask & AE_WRITABLE) ee.events |= EPOLLOUT; // 写事件 ee.data.fd = fd; epoll_ctl(state->epfd, op, fd, &ee); // O(log n) } // 3. 等待就绪事件 static int aeApiPoll(aeEventLoop *eventLoop, struct timeval *tvp) { int numevents = epoll_wait(state->epfd, state->events, setsize, timeout); // 只返回就绪的 fd, O(1) for (int i = 0; i < numevents; i++) { int mask = 0; if (state->events[i].events & EPOLLIN) mask |= AE_READABLE; if (state->events[i].events & EPOLLOUT) mask |= AE_WRITABLE; eventLoop->fired[i].fd = state->events[i].data.fd; eventLoop->fired[i].mask = mask; } return numevents; }
Redis 为什么选 LT 而非 ET： LT 模式下，如果一次 read() 没读完缓冲区，下次 epoll_wait 仍会通知， 编程更简单安全。ET 模式虽然性能略高，但要求非阻塞循环读取直到 EAGAIN， 在 Redis 的单线程模型中收益有限，反而增加复杂度。
