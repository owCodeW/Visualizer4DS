Redis 缓存三大问题

缓存穿透

描述： 查询一个根本不存在的数据，缓存层和数据库都没有命中。恶意攻击或大量非法key导致请求直接打到数据库，压垮DB。
成因分析
  • 业务层校验不严谨，查询了数据库中不存在的数据ID。
  • 业务层面：新上线的业务缓存和数据库中不存在该数据
  • 恶意攻击/爬虫使用不存在的key高频访问。
  • 缓存形同虚设，每次请求都绕开缓存直达DB。
解决方案
  • 布隆过滤器 (BloomFilter)在缓存前加一层过滤器，拦截不存在key。
  • 缓存空对象 将null结果短暂缓存（如几分钟），避免反复穿透。
  • 接口层加强参数校验，限制非法key频率/模式。

缓存击穿

描述： 某个热点Key在失效的瞬间，大量并发请求同时查询该key，缓存未命中，全部请求涌入数据库，导致DB压力瞬间飙升。
成因分析
  • 热点数据设置了过期时间，在高并发时刻突然失效。
  • 海量线程同时重建缓存，未做并发控制，DB被击穿。
  • 类似秒杀、爆款商品详情页，缓存重建代价昂贵。
解决方案
  • 互斥锁 (Mutex) 只允许一个线程重建缓存，其余等待/重试。
  • 逻辑过期 不设置物理过期，后台异步刷新热点数据。
  • 永不过期策略 + 定时更新，结合熔断降级保护DB。

缓存雪崩

描述： 缓存中大量Key在同一时间段集体失效，或Redis节点宕机，导致海量请求直接击穿至数据库，引发连锁故障甚至服务雪崩。
成因分析
  • 大量key设置了相同的过期时间（如整点失效）。
  • Redis单点故障或网络分区导致缓存不可用。
  • 预热期不足，高峰期缓存大面积缺失。
解决方案
  • 过期时间随机化 — 基础时间上加随机偏移，避免集体失效。
  • 高可用集群 (Redis Sentinel/Cluster) 避免单点故障。
  • 多级缓存 + 熔断降级 (本地缓存Caffeine/Hystrix限流)。
  • 缓存预热 & 持久化备份，搭配请求限流。

三者核心区别 & 应对策略总览

穿透：查无此key
👉 方案：布隆过滤器 + 空对象缓存
击穿：热点key失效瞬间
👉 方案：互斥锁/逻辑过期/后台异步
雪崩：大量key同时失效/Redis宕机
👉 方案：随机TTL + 集群 + 熔断降级
高并发场景下，推荐组合拳：布隆过滤器 + 热点永不过期 + 随机的过期时间 + 限流兜底 分布式架构中善用 Redisson / Sentinel 等组件
